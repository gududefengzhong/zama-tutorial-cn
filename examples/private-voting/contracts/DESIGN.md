# Contract Design

这个文档用于把“私密投票最小版”的合约设计提前固定下来。

目标不是现在就实现所有细节，而是先把边界画清楚，避免后续一边写代码一边改模型。

## 第一版合约目标

第一版合约只负责最小业务闭环：

- 初始化一次投票
- 接收用户投票
- 阻止重复投票
- 在结束后公开结果

## 建议的公开状态

这些状态可以优先设计成公开可读：

- 投票标题
- 候选项名称列表
- 投票开始时间
- 投票结束时间
- 某地址是否已投票
- 投票是否已结束
- 最终结果是否已公开

这样做的好处是：

- 前端读取简单
- 测试更容易写
- 读者更容易分清业务流程和隐私逻辑

## 建议的私密状态

第一版建议把下面这些状态视为私密逻辑的核心：

- 用户具体投给了哪个候选项
- 每个候选项在投票过程中的票数累计

如果后续实现中决定“结束后公开总票数”，也要在教程中说明这是“结束后可公开”，而不是“全过程公开”。

## 建议的函数职责

### `constructor` 或初始化函数

负责设置：

- 投票标题
- 候选项
- 时间窗口

### `vote(...)`

负责：

- 检查投票是否在有效期内
- 检查调用者是否已经投票
- 接收并处理私密投票输入
- 更新私密计票状态
- 把调用者标记为已投票

### `finalize()` 或等效函数

负责：

- 检查投票是否已经结束
- 将结果切换到可公开阶段
- 为后续结果读取做准备

### 公开读取函数

建议第一版只提供最必要的读取能力，例如：

- 获取投票元信息
- 获取候选项名称
- 查询某地址是否已投票
- 在结果公开后读取最终统计

## 需要在教程中反复强调的边界

### 已投票状态是否必须私密

第一版里不必强行做成私密。  
因为它更像流程控制状态，而不是业务敏感值。

### 最终结果是否必须永远私密

不一定。  
对“私密投票”来说，更常见的目标是：

- 过程私密
- 结果在规则允许的时间点公开

### 单个用户投票记录是否应该公开

第一版建议不要公开。  
这正是示例的核心隐私价值之一。

## 第一版不做的事情

为了把范围收紧，先明确不做这些功能：

- 多投票实例管理
- 复杂权限角色
- 可撤回投票
- 委托投票
- 候选项动态增删
- 丰富事件设计

这些内容都可以作为第二阶段扩展，而不应该压到第一个版本里。
