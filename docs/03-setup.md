# 03. 环境搭建

## 本章目标

这一章的目标不是把所有工具名都罗列一遍，而是帮助读者真正完成一件事：

把一个可用于 Zama / FHEVM 开发的本地环境准备好，并且知道后面应该从哪里开始写代码、跑测试、做部署。

结合当前官方资料，比较稳妥的入门路线是：

- 使用 Hardhat
- 基于 Zama 提供的 `fhevm-hardhat-template` 开始
- 先在本地完成编译和 mocked mode 测试
- 再考虑连接 Sepolia 等真实网络

这条路径对中文区开发者比较友好，因为它和现有 Solidity / Hardhat 经验衔接最好。

本教程默认先帮助读者完成“本地链 + mocked mode + 本地前端”的最小闭环。  
如果读者之后想继续验证真实网络交互，再自行部署到 Sepolia 即可；教程本身不会要求预置测试网地址。

## 你需要先准备什么

在正式开始前，建议确认下面几件事：

- 你已经有基本的 Solidity / Hardhat 使用经验
- 你本机已经安装 Node.js 和 npm
- 你知道如何使用 Git 克隆一个模板仓库
- 你有一个常用的钱包，例如 MetaMask

如果你完全没有 Hardhat 经验，建议先补一点最基础的 Hardhat 知识，再回来读这部分。因为后面的编译、测试、部署、脚本执行都会围绕 Hardhat 展开。

## 推荐环境

根据 Zama 当前文档和官方模板，推荐使用下面这组基础环境：

- Node.js LTS 版本
- 偶数版本的 Node.js，例如 `v18.x` 或 `v20.x`
- npm、pnpm 或 yarn 中任选其一
- Git

这里有一个非常重要的提醒：

Hardhat 不推荐使用奇数版本 Node.js。如果你本机是 `v21.x`、`v23.x` 这类版本，即使能跑，也可能遇到警告或不稳定问题。做教程时一定要明确写出来，否则读者会在最开始就踩坑。

## 第一步：检查本机基础环境

先在终端里确认 Node.js 和 npm 可用：

```bash
node -v
npm -v
```

如果你拿到的不是一个稳定的偶数版本 Node.js，建议先切换到 LTS 版本再继续。

对中文读者来说，一个很实用的写法是直接在教程里提醒：

- 不要用太新的实验性版本
- 优先用团队里最常见的 LTS 版本
- 如果后续遇到莫名其妙的问题，先回头检查 Node 版本

## 第二步：从官方模板开始，而不是手搓

如果你的目标是快速上手 Zama / FHEVM，最推荐的方式不是从零配置一个 Hardhat 工程，而是直接从官方模板开始。

这样做的好处很明显：

- 官方已经把基础依赖关系整理好了
- 目录结构更接近文档示例
- 测试、部署和插件配置的踩坑成本更低

官方当前推荐的模板是 `zama-ai/fhevm-hardhat-template`。

你可以用两种方式开始：

### 方式一：在 GitHub 上使用模板创建自己的仓库

适合想长期维护教程示例或项目仓库的人。

大致流程是：

1. 打开官方模板仓库
2. 点击 `Use this template`
3. 创建你自己的新仓库
4. 再克隆到本地

### 方式二：先直接克隆模板做本地实验

适合你先想快速验证流程。

```bash
git clone <你的模板仓库地址>
cd <项目目录>
```

在中文教程里，建议你优先推荐“从模板创建自己的仓库”这条路径。因为很多读者后面会直接在这个仓库上改造成自己的 demo。

## 第三步：安装依赖

进入项目根目录后，安装依赖：

```bash
npm install
```

这一步完成后，项目的基础 Hardhat 开发环境就已经就绪了。

如果这里失败，常见原因通常不是 Zama 本身，而是这些更基础的问题：

- Node 版本不对
- npm 源或网络环境有问题
- 本机已有缓存导致依赖冲突
- 某些系统工具链没有准备好

所以在教程里最好把“先排查基础环境，再怀疑 FHE 依赖”写清楚。

## 第四步：先理解本地开发和真实网络的区别

很多新手会默认以为：“能编译就等于能完整体验 Zama。”

实际上你应该把开发流程拆成两层：

- 本地开发层：以快速迭代、跑测试、验证合约逻辑为主
- 真实网络层：以真实部署、真实交互、真实链路验证为主

官方模板里非常重要的一点，是支持 mocked mode。

你可以先把 mocked mode 理解成：

一种更适合开发和测试的本地模式，它让你能够更快地验证合约逻辑，而不用一开始就把全部注意力放到真实网络环境上。

这对教程尤其重要，因为它能显著降低读者第一次上手的阻力。

## 第五步：先跑通编译和测试

在教程中，环境搭建是否成功，不应该用“依赖装完了”来判断，而应该用“最基本的工程命令是否跑通”来判断。

一个最小检查清单可以是：

```bash
npm run compile
npm run test
```

如果这两步能跑通，说明至少以下几件事已经成立：

- Hardhat 工程结构基本正常
- 依赖已经安装完整
- 合约和测试框架可以工作
- 你已经拥有继续改造示例的最小基础

对读者来说，这比“看到一堆文件目录”更有安全感。

## 第六步：本地节点与部署

当编译和测试正常后，再进入本地部署阶段会比较顺。

官方模板给出的本地工作流大致是：

```bash
npx hardhat node
npx hardhat deploy --network localhost
```

可以把这两步理解为：

- 先启动一个本地开发链环境
- 再把示例合约部署进去

在教程里你可以明确提醒读者：  
这一步的目标不是“上线”，而是把完整链路第一次跑通。

## 第七步：什么时候需要配置 Sepolia

如果你只是学习概念、调试示例、写最小版教程，其实完全可以先停留在本地。

对这套中文教程来说，Sepolia 明确是一个“可选的进阶路径”，不是入门必做项。  
我们更希望读者先把本地合约、测试和前端展示流程跑顺，再自己决定是否继续部署测试网。

只有当你准备做下面这些事情时，才需要继续配置真实网络：

- 部署到 Sepolia 测试网
- 演示更接近真实环境的交互
- 让前端直接连测试网络做展示
- 验证从部署到交互的完整链路

根据官方模板的说明，想连接 Sepolia，通常至少要准备这些变量：

- `MNEMONIC`
- `INFURA_API_KEY`

可选还包括：

- `ETHERSCAN_API_KEY`

对应命令通常类似：

```bash
npx hardhat vars set MNEMONIC
npx hardhat vars set INFURA_API_KEY
npx hardhat vars set ETHERSCAN_API_KEY
```

这里建议在教程里单独提醒一句：

默认值只适合本地或示例场景，不适合真实部署。

## 建议读者先做到什么程度

如果你是第一次接触 Zama / FHEVM，我建议先不要把目标定得太重。完成下面四件事，就已经非常好了：

1. 成功创建一个基于官方模板的工程
2. 成功安装依赖
3. 成功运行编译和测试
4. 看懂模板中的合约、测试和部署目录分别在做什么

做到这一步，再开始改写自己的私密投票示例，会顺很多。

## 推荐的目录理解方式

一个基于 Hardhat 模板的项目，通常可以先这样理解：

- `contracts/`：智能合约源码
- `test/`：测试脚本
- `deploy/`：部署脚本
- `tasks/`：自定义 Hardhat 任务
- `hardhat.config.ts`：工程配置
- `package.json`：依赖与脚本入口

对教程作者来说，最重要的是不要一口气讲所有文件。  
建议先只带读者看三类内容：

- 合约在哪里
- 测试怎么跑
- 部署命令从哪里触发

剩下的内容随着案例推进再展开。

## 本章常见坑

### 1. Node 版本不合适

现象：

- 安装依赖时有奇怪警告
- Hardhat 提示版本不推荐
- 本地命令行为不稳定

解决思路：

- 切换到偶数版本 LTS Node.js
- 重新安装依赖

### 2. 以为必须一开始就跑真实网络

现象：

- 一上来就配置钱包、RPC、测试币
- 环境还没跑通就陷入网络问题

解决思路：

- 先用 mocked mode 和本地流程建立信心
- 把真实网络放到第二阶段

### 3. 把“模板工程可运行”误解成“我已经理解 FHE 应用了”

现象：

- 工程能跑，但读不懂输入、权限和结果可见性

解决思路：

- 把模板当作起点，而不是终点
- 后续一定要用一个完整案例把抽象概念串起来
