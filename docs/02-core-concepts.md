# 02. 核心概念

## 本章目标

这一章的任务很明确：先建立一套足够稳的心智模型，再去碰代码。

很多人第一次看 Zama / FHEVM 资料时会卡住，不是因为代码有多难，而是因为概念层面没有形成一个连续的画面。看起来每个词都认识，但放到一起就不确定“数据到底是怎么流动的”。

所以这一章我们重点解决四件事：

- 什么是明文和密文
- 什么是加密输入
- 什么是合约中的密文状态与密文计算
- 什么是查看权限，以及它为什么会成为应用设计的一部分

## 先把最朴素的区别想清楚：明文 vs 密文

在普通应用开发里，我们默认处理的是明文数据。  
比如用户输入 `42`，后端看到的是 `42`，数据库里存的是 `42`，前端读出来展示的也是 `42`。

而在隐私计算语境下，你需要学会区分两种状态：

- 明文：可以直接读取和理解的数据
- 密文：已经被加密，不能直接从表面看出原始值的数据

这个区别听起来很基础，但它会直接影响你后面对合约状态的理解。

在普通智能合约里，我们会天然觉得：

- 一个状态变量写进链上
- 那它就应该是可读的
- 前端只要调用 view 方法就能拿到值

但在 FHE 的心智模型里，这个默认前提不再成立。某个值即使已经进入合约状态，也不意味着任何人都能直接读到它的原始内容。

## FHE 的关键点，不是“把数据加密存起来”

很多人第一次接触时会误以为：  
“这不就是把变量加密后存进链上吗？”

如果只是“加密存储”，那只能解决一部分问题。真正困难的地方在于：应用不是为了存储而存在，应用是为了计算而存在。

投票要计票，竞价要比较大小，余额要参与规则判断，游戏状态要推动下一步逻辑。如果数据一旦加密就完全无法参与后续逻辑，那它对链上应用的帮助就非常有限。

所以 FHE 的核心意义可以先粗略理解为：

让系统有机会对密文状态继续进行计算，而不是每次一计算就必须先把原文暴露出来。

你现在不需要记住任何数学细节，只要抓住这层“密文还能参与逻辑”的直觉就够了。

## 一个开发者视角的数据流

先看一个非常简化的思维流程：

1. 用户在前端输入一个原始值
2. 这个值在进入合约逻辑前，被处理成适合隐私计算的输入形式
3. 合约在密文状态上执行某些规则
4. 某些结果可能继续保持密文
5. 只有被允许的角色，才能在合适的时候看到对应结果

如果你把这五步理解成一个“隐私数据的生命周期”，后面很多概念就都能对上位置了。

## 什么是加密输入

在普通 dApp 里，用户向合约提交参数时，开发者通常把它理解成一笔普通交易输入。  
例如投票时传一个候选人编号，竞价时传一个数字，转账时传一个金额。

但在 Zama / FHEVM 的场景里，读者需要意识到：  
“输入参数”这件事本身也分成两种思路。

- 普通输入：参数以明文形式参与链上执行
- 加密输入：参数在进入主要合约逻辑时，已经不再是普通明文视角

这对开发的影响非常直接：

- 你不能再简单假设前端表单值会一比一映射成链上公开参数
- 你需要理解前端、钱包、合约之间在输入处理上的配合
- 你需要在教程中明确告诉读者：数据从 UI 到链上，中间到底发生了什么

后面写代码时，我们会重点把“用户输入如何变成合约可处理的私密输入”讲透，这通常是新手第一次真正上手时最容易卡住的部分。

## 什么是密文状态

密文状态可以先理解成：  
合约里有一些状态变量，它们代表真实业务状态，但外界不能像读普通公开变量那样直接拿到原始值。

比如在私密投票里，你可能关心这些信息：

- 某个用户是否已经投票
- 某个候选人的票数
- 当前投票是否已经结束

其中并不是所有东西都必须保密。

一个常见而健康的设计方式是：

- 流程控制状态尽量公开
- 用户敏感输入和关键统计状态尽量私密

这也是做 Zama 应用时很重要的工程意识：  
不要把所有内容都想成“越私密越好”，而是要有选择地定义哪些信息应该公开、哪些信息应该保密。

## 什么是密文计算

密文计算的关键直觉是：

合约逻辑并不是完全失明的。它虽然不能像处理普通明文那样随意读取原始值，但仍然可以在受支持的能力范围内对这些值执行规则。

对开发者来说，这意味着你在写业务逻辑时要逐渐适应一种新感觉：

- 你知道系统里“有这个值”
- 你也知道这个值会影响逻辑
- 但你不一定能像调试普通 Solidity 那样，随时把它打印出来看

这会带来两个直接变化。

第一，代码设计要更克制。  
你需要更清楚地定义哪些逻辑必须依赖密文状态，哪些逻辑可以留在公开层完成。

第二，调试思维要改变。  
你不能总想着“把状态打出来看看”，而要更多依赖流程拆解、辅助日志、测试用例和最小路径验证。

## 查看权限为什么是核心概念

在普通链上应用里，“读取”往往是一个默认动作。只要数据上链，任何人都可能通过节点、区块浏览器或 RPC 接口去看。

但在 Zama 这一类应用里，读取能力本身不再是默认公共能力，而更像一种需要被设计和授予的权限。

你可以把它理解成两个不同的问题：

- 系统能不能基于某个值继续执行逻辑
- 某个参与方能不能看到这个值的原始内容

这两个问题不再等价。

这也是为什么我们后面做私密投票时，必须单独考虑：

- 投票者本人能看到什么
- 合约拥有怎样的处理能力
- 管理者能看到什么
- 最终公开展示的结果应该精确到什么程度

如果你把“权限设计”只当成传统的 `onlyOwner` 或角色控制来理解，通常是不够的。因为这里还涉及“谁能看见什么”。

## 一个最简单的思维对照

普通 dApp 的默认心智模型常常是：

- 数据公开
- 逻辑公开
- 结果公开

而 FHE 应用更接近：

- 规则可以公开
- 部分输入可以私密
- 部分中间状态可以私密
- 最终结果是否公开、对谁公开，需要单独设计

这就是为什么你会感觉这类应用更像“系统设计问题”，而不只是“写几个合约函数”。

## 为什么开发和调试会更不直观

做普通合约时，我们很习惯这些动作：

- 直接读取状态变量
- 看事件日志
- 用脚本快速 dump 当前状态
- 在前端里马上展示返回值

但一旦状态涉及密文，很多“理所当然”的调试动作都会失效或变得不完整。你可能会遇到这种体验：

- 交易成功了，但你不能直接肉眼确认某个内部值
- 合约逻辑跑了，但你需要借助额外路径确认业务结果
- 前端不是“读到什么就展示什么”，而是要结合权限决定能展示什么

所以做这类应用时，建议尽早建立两个习惯：

- 每次只验证一小段完整路径
- 先保证数据流正确，再追求功能堆叠

这也是为什么我们的教程会先做最小版私密投票，而不是上来就做复杂功能组合。

## 常见误解

### 误解一：密文状态等于完全不可用

不是。它不是“不能参与逻辑”，而是“不能用普通明文直觉去使用”。

### 误解二：只要是隐私应用，就应该所有状态都加密

也不是。好的系统设计通常会把公开状态和私密状态分层，而不是一刀切。

### 误解三：权限只是管理员权限

不够。这里的权限还包括查看能力、结果可见性和交互边界。

### 误解四：先把 API 背下来就能开工

通常不行。如果不理解输入、状态、计算、查看之间的关系，API 只会越学越乱。

## 一个适合记住的小框架

接下来几章里，你可以一直用下面这个四步框架来理解每个示例：

1. 数据从哪里来
2. 它以什么形式进入合约
3. 合约如何在不暴露原文的前提下处理它
4. 最终谁能看到什么结果

无论是私密投票、密文竞价，还是隐私余额，这四个问题都会反复出现。

## 这一章你应该带走什么

如果你只想记住最核心的内容，可以记下面四句话：

1. FHE 的关键不是“把数据藏起来”，而是“让密文仍然有机会参与计算”。
2. Zama 应用的重点不只是函数调用，而是输入、状态、计算和查看权限的完整链路设计。
3. 不是所有状态都应该保密，好的工程实践是分层设计公开信息和私密信息。
4. 开发这类应用时，调试方式会比普通合约更间接，需要更强的数据流意识。
