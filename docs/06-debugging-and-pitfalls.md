# 06. 调试与常见坑

## 本章目标

这一章不讲新概念，也不追求炫技。  
它的目标只有一个：让读者少走弯路。

Zama / FHEVM 教程最容易失败的地方，不是概念讲不清，而是读者刚开始动手就不断踩坑，最后在“是不是我自己太菜了”的情绪里放弃。

所以这一章会用一个更实用的结构来写：

- 先看现象
- 再判断最可能的原因
- 最后给出排查顺序

## 先记住一个总原则：先分层定位，再局部排查

一旦你开始做私密应用，问题来源通常不只一层。

同一个“页面上没看到结果”，背后可能是：

- 环境问题
- 依赖问题
- 合约逻辑问题
- 前端状态同步问题
- 时间窗口判断问题
- 权限或可见性边界问题

如果一上来就盲改代码，通常只会越改越乱。

更稳的做法是先把问题分到层：

1. 是环境没起来
2. 还是合约没按预期执行
3. 还是前端没正确表达链上状态
4. 还是你预期看到的内容本来就不该在当前阶段可见

很多所谓“神秘 bug”，其实只是最后一种。

## 第一类：环境安装和依赖问题

### 现象

- `npm install` 失败
- Hardhat 启动时报版本警告
- 编译命令直接报错
- 本地节点跑不起来

### 常见原因

- Node.js 版本不合适
- 依赖没有完整安装
- 锁文件和依赖树不一致
- 把模板仓库要求的运行环境理解错了

### 建议排查顺序

1. 先检查 Node.js 版本
2. 再确认依赖是否完整安装
3. 再看是不是模板和本地工具版本不兼容

### 最实用的提醒

如果你一开始就遇到大量“很底层”的错误，不要先怀疑 FHE 逻辑。  
优先把它当成普通 JavaScript / Hardhat 工程问题来处理。

## 第二类：编译通过，但你其实还没真正跑通

### 现象

- `compile` 能过
- 但 `test` 失败
- 或者本地部署成功，交互却不对

### 常见原因

- 你只验证了语法，没有验证行为
- 合约接口变了，但测试或前端没同步
- 本地 mocked mode 和你想象中的真实链路不是一回事

### 解决思路

把“编译通过”只当作起点，而不是完成标志。

更可靠的最小闭环应该是：

1. 编译通过
2. 主流程测试通过
3. 本地部署成功
4. 至少一次完整交互成功

只有这四步都成立，才算真正“跑起来”。

## 第三类：输入流程看起来没问题，但业务结果不对

### 现象

- 用户发起投票后交易成功
- 但后续状态和你预期不同
- 或者结果迟迟没有变化

### 常见原因

- 输入处理路径理解错了
- 合约虽然收到交易，但更新的不是你以为的那个状态
- 前端展示的是旧状态
- 投票时间窗口判断和你预期不一致

### 建议排查方式

不要第一时间盯着“结果值”看，先回到流程：

1. 交易是否真的发送成功
2. 合约是否进入了正确函数
3. 公开状态是否发生了预期变化
4. 当前阶段本来是否允许看到最终结果

这个顺序很重要。  
因为在隐私应用里，“没看到结果”并不自动等于“逻辑错了”。

## 第四类：明明是正常行为，却被误判成 bug

这是中文读者最容易卡住，也最值得在教程里提前点破的一类。

### 典型现象

- 页面上看不到票数
- 结果区域显示“暂不可见”
- 某些状态不能像普通 dApp 一样直接读取

### 实际上可能是

- 投票还没结束
- 结果本来就被设计成结束后公开
- 当前角色本来就不该看到这个值

### 教程里要明确告诉读者

在 FHE 应用里，“当前不可见”本身就是业务规则的一部分。  
只要系统表达得足够清楚，它就不是 bug。

## 第五类：时间相关问题

### 现象

- 前端显示还能投，合约却拒绝
- 测试里能投票，页面上却提示已结束
- 结束逻辑触发时间和预期不同

### 常见原因

- 把本地时间当成链上时间
- 测试中手动推进时间，但前端没有同步对应逻辑
- 没有明确区分“开始前”“进行中”“结束后”三个状态

### 解决方式

建议所有教程示例都把时间问题显式化：

- 页面文案明确当前所处阶段
- 测试分别覆盖开始前、进行中、结束后
- 不要把“当前时间判断”藏在很深的工具函数里

时间问题在普通 dApp 里就已经常见，在投票这种流程型应用里只会更明显。

## 第六类：前端联调问题

### 现象

- 合约测试通过，但页面行为异常
- 钱包连接正常，但投票按钮状态不对
- 交易发出后，页面迟迟不刷新

### 常见原因

- 前端读取的是旧缓存
- 钱包状态、链状态和本地 UI 状态没有对齐
- 交易发出后没有在正确时间重新获取公开状态
- 错把“未公开结果”渲染成“空数据”

### 排查思路

把前端问题拆成三层：

1. 钱包层：连接了吗，网络对吗
2. 交易层：发送了吗，确认了吗
3. 展示层：页面根据链上状态切换了吗

这样你就不会把所有异常都怪到合约头上。

## 第七类：测试写得太快，反而失去帮助

### 现象

- 测试很多，但一看就不知道在验证什么
- 出错时无法快速定位业务规则
- 一改代码就连锁失败

### 常见原因

- 测试没有围绕用户流程写
- 把多个行为塞进一个大用例
- 混合验证公开状态、私密状态、时间状态，导致意图模糊

### 更好的写法

优先围绕业务问题组织测试：

- 是否能创建投票
- 是否能成功投票
- 是否能阻止重复投票
- 是否在正确时间公开结果

这样不仅更容易维护，也更适合拿来当教程内容。

## 一个很好用的最小排查清单

当你卡住时，按这个顺序查通常最有效：

1. 当前 Node.js 和依赖环境是否正常
2. `compile` 是否通过
3. `test` 是否通过
4. 本地部署是否成功
5. 公开状态是否符合预期
6. 当前阶段是否本来就不应看到结果
7. 前端是否正确刷新和表达了状态

这比“凭直觉乱改”稳定得多。

## 中文教程特别值得补的 FAQ

如果你后面继续完善仓库，建议把下面这些问题沉淀成 FAQ：

- 为什么我在页面上看不到票数
- 为什么交易成功了但结果没有立刻更新
- 为什么本地能跑，换到测试网就出问题
- 为什么我能读到投票元信息，却读不到内部结果
- 为什么前端提示失败，但链上其实已经发出交易

这些都是非常典型、也非常适合帮助中文读者建立信心的问题。

## 本章最重要的结论

如果要把这一章压缩成一句话，那就是：

不要把 FHE 应用的问题想得过于神秘。  
大多数问题依然可以按“环境、合约、时间、前端、权限”这几个层次来拆。

你真正要学会的，不是某个神秘调试技巧，而是更冷静地判断：

- 现在坏的是哪一层
- 这是不是 bug
- 还是系统本来就该这样工作
