# 07. 从 Demo 到项目

## 本章目标

如果前六章帮助读者完成的是“理解并跑通一个示例”，那么这一章要解决的是另一件更现实的事情：

如何把你学到的这些东西，转化成一个真正能推进的项目。

这一步非常关键。  
因为很多教程在“Hello World 跑通”之后就结束了，但真正的价值恰恰发生在之后：

- 你怎么判断一个需求值不值得用 FHEVM
- 你怎么缩小第一版范围
- 你怎么安排测试、演示和上线节奏
- 你怎么避免做成一个概念很好听、但工程上无法推进的项目

## 第一个问题：不是所有需求都适合 FHEVM

这是做项目时最重要的判断。

一个需求更适合 FHEVM，通常意味着它同时满足下面几个条件：

- 链上规则执行是刚需
- 数据隐私不是装饰，而是产品成立条件
- 中间状态或输入如果公开，会明显破坏体验或公平性
- 团队愿意接受更高的工程复杂度

典型例子包括：

- 私密投票
- 密文竞价
- 隐私积分或隐私余额
- 某些链上游戏中的隐藏状态
- 商业敏感数据参与链上规则执行的场景

反过来说，如果一个需求是下面这种，就应该先谨慎：

- 状态本来就应该完全公开
- 项目更在意低成本和快速交付
- 团队还没准备好处理复杂链路和调试成本
- 用更简单的链下或半链下方案就足够

技术选型最怕的不是“选得保守”，而是“为了先进而先进”。

## 第二个问题：怎么判断隐私到底值不值得这份复杂度

你可以问自己五个问题：

1. 如果数据公开，产品会不会失去核心价值
2. 如果中间状态被观察到，会不会影响公平性或策略空间
3. 用户是否真的会因为隐私保护而更愿意使用这个产品
4. 团队是否能承受更高的开发、测试和解释成本
5. 有没有更简单的替代方案已经足够

如果前面三题大多是“是”，后面两题也能接受，那么这个方向通常值得继续往下做。

## 第三个问题：第一版项目到底应该做多大

大多数项目死在第一版太大，而不是太小。

对于刚做 FHEVM 的团队，最推荐的不是“做一个功能完整的平台”，而是“做一个边界清晰的 MVP”。

一个好的 MVP 通常要满足三点：

- 能清楚体现隐私价值
- 能在较短时间内跑通完整流程
- 能被外部用户或团队成员一眼看懂

## 一个适合中文团队的 MVP 模板

你可以直接用下面这个模板去定义第一版项目。

### 1. 核心场景

只回答一个问题：

用户到底要完成什么动作？

例如：

- 参与一次私密投票
- 提交一次密文出价
- 查看一次受权限保护的结果

### 2. 必要角色

第一版尽量压缩角色数量。

例如：

- 普通用户
- 发起者 / 管理者

先不要一开始就做复杂权限系统。

### 3. 最小成功标准

先定义什么叫“做成了”。

例如对私密投票来说，可以是：

- 用户可以成功投票
- 投票过程中的敏感数据不会提前公开
- 投票结束后能看到最终结果

### 4. 明确不做什么

这一步往往比“要做什么”还重要。

比如第一版先不做：

- 多实例管理
- 复杂身份验证
- 移动端适配
- 多语言切换
- 复杂运营后台

## 第四个问题：怎么设计公开信息和私密信息

这是项目化阶段最重要的架构动作之一。

一个很实用的原则是：

- 公开信息尽量公开
- 只有真正影响隐私价值的部分才进入私密链路

这样做有三个好处：

- 前端和测试都更简单
- 用户更容易理解系统
- 性能和工程复杂度更可控

你可以在设计阶段直接列两张表：

### 公开信息表

- 标题
- 描述
- 时间窗口
- 是否已参与
- 是否已结束

### 私密信息表

- 用户具体输入
- 过程中不应暴露的统计状态
- 只应在特定条件下公开的结果

如果这两张表列不清楚，通常说明需求还没想明白。

## 第五个问题：如何安排工程推进顺序

一个比较稳的推进顺序通常是：

1. 先固定业务边界
2. 再写合约的最小公开结构
3. 再接入私密输入和私密状态
4. 先用 mocked mode 写测试
5. 再补 localhost 部署和前端联调
6. 最后再考虑 Sepolia 演示和更复杂功能

这个顺序看起来偏慢，但实际上更快。  
因为它避免了你同时在“概念、实现、网络、前端”四层里一起迷路。

## 第六个问题：怎么安排测试和验证

做 FHEVM 项目时，测试策略最好分三层。

### 第一层：合约行为测试

验证业务规则有没有成立，例如：

- 是否能投票
- 是否能防止重复投票
- 是否在正确时间开放或关闭行为

### 第二层：本地流程验证

验证完整交互链路，例如：

- 本地节点是否能部署
- 前端能否连接并提交
- 页面状态是否正确切换

### 第三层：测试网演示验证

验证更接近真实环境的行为，例如：

- 钱包交互是否正常
- 配置是否正确
- 更真实网络延迟下，状态提示是否合理

如果一开始就跳第三层，通常会浪费很多精力。

## 第七个问题：怎么管理团队预期

如果这是一个团队项目，而不只是个人学习，预期管理非常重要。

你最好尽早告诉团队这些事实：

- 这不是普通 Solidity 项目难度的线性增加
- 隐私价值会带来额外的开发和调试复杂度
- 第一个版本应该优先追求“能解释、能演示、能验证”
- 不要一开始就承诺过大的功能范围和交付时间

这并不是保守，而是成熟。

## 第八个问题：怎么判断项目已经进入“可对外展示”阶段

一个项目不一定要功能很多，才值得展示。

如果它已经满足下面几条，就很适合拿去做分享、演示或招募协作者：

- 核心场景清楚
- 隐私价值直观
- 主要流程能稳定跑通
- 页面和文案能解释系统当前状态
- 你能清楚说明哪些是第一版、哪些是后续规划

对中文区项目尤其如此。  
一个“能讲清楚为什么需要它、怎么工作、现在能做到什么”的项目，往往比一个功能很多但解释不清的项目更有传播力。

## 几个很适合继续扩展的项目方向

如果你想在私密投票之后继续扩展，下面几个方向都很不错：

- 密文竞价系统
- 隐私积分榜
- 受权限控制的链上数据看板
- 链上游戏中的私密属性系统
- 团队或社区治理中的隐私协作工具

建议每次只选一个方向深入，不要同时铺很多线。

## 一份可以直接照着用的项目推进清单

你可以把下面这份清单当作教程最后的“行动版结尾”。

1. 先用一句话定义你的产品目标
2. 写出公开信息和私密信息两张表
3. 列出第一版只支持的 3 到 5 个功能
4. 明确第一版不做什么
5. 先完成合约和 mocked mode 测试
6. 再完成 localhost 部署和前端联调
7. 最后再准备测试网演示

如果你能把这七步做完，一个真正可推进的 FHEVM 项目雏形通常就出来了。

## 整套教程的最终结论

走到这里，读者最应该带走的，不是某几个 API 名字，而是下面这些更底层的判断：

1. Zama 值得学，因为它打开了“链上规则执行 + 数据隐私保护”的新设计空间。
2. 学这类技术，关键不只是写合约，而是理解输入、状态、权限、结果和前端表达之间的完整链路。
3. 做项目时，范围控制比功能堆叠更重要。
4. 一个好的 FHEVM 项目，应该先做成“可以解释、可以验证、可以演示”，再逐步做大。

## 这之后你最适合做什么

如果你已经完整读完这套教程，接下来的最佳动作通常不是继续看更多概念，而是马上做一件具体的小事：

- 把私密投票案例真正实现出来
- 或者把它改造成你自己的第一个隐私场景

因为从这一步开始，真正帮助你成长的将不再只是阅读，而是亲手把“公开状态、私密状态、测试、前端、部署”这些部分拼到一起。
