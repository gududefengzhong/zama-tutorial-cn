# 05. 完整 dApp

## 本章目标

前一章我们完成了“第一个 Demo 应该怎么设计”的讨论，这一章往前再走一步：

把“私密投票最小版”升级成一个可以向外展示、可以继续扩展、也更接近真实产品结构的完整 dApp。

这里的重点不是做一个功能很多的系统，而是让读者理解一件事：

一旦进入完整应用阶段，Zama / FHEVM 的难点就不再只在合约本身，而是在合约、前端、权限、时间流程和结果展示之间的整体配合。

## 从 Demo 到 dApp，究竟多了什么

在最小 Demo 里，我们重点关注的是：

- 这个问题值不值得用隐私计算
- 哪些状态公开，哪些状态私密
- 用户能不能完成一次正确的投票

而到了完整 dApp 阶段，你需要开始考虑更完整的产品视角：

- 用户如何知道当前投票正在进行
- 用户如何理解哪些结果现在能看、哪些暂时不能看
- 合约时间窗口如何和前端页面状态同步
- 钱包连接、交易发送、结果刷新如何串起来
- 出错时用户看到的是什么体验

也就是说，完整 dApp 的关键不只是“功能更多”，而是“系统边界更清楚、交互更完整、状态表达更一致”。

## 为什么私密投票仍然是最好的主线案例

到了这个阶段，私密投票的优势会更明显。

因为它天然包含一个完整 dApp 应该具备的几层结构：

- 一层公开信息：标题、候选项、时间、是否结束
- 一层私密逻辑：用户投票意图、进行中的计票过程
- 一层权限与可见性：什么时间、由谁看到什么结果
- 一层前端交互：连接钱包、提交投票、查看状态、等待最终结果

相比之下，如果你用“私密计数器”做完整 dApp，会很难把这些层次讲完整。

## 完整 dApp 建议拆成哪几层

为了让中文读者更容易建立清晰结构，建议把完整 dApp 拆成四层来讲。

### 第一层：合约层

这一层负责回答：

- 业务规则是什么
- 哪些状态上链
- 哪些状态公开
- 哪些状态私密
- 时间窗口如何约束行为

在私密投票里，合约层最重要的职责通常包括：

- 初始化投票元信息
- 校验用户是否有资格投票
- 处理投票输入
- 防止重复投票
- 在投票结束后切换结果展示阶段

### 第二层：前端交互层

这一层负责回答：

- 用户现在在做什么
- 页面应该引导用户完成什么动作
- 哪些信息应该直接展示
- 哪些信息应该提示“暂不可见”

很多新手做 FHE 应用时会本能地沿用普通 dApp 的前端思维：

- 页面加载
- 调 `view`
- 拿值
- 展示

但在私密应用里，这条路径不再总是成立。前端需要明确表达“看不到”也是一种正常状态，而不是错误。

### 第三层：状态同步层

这一层经常被忽视，但它对体验影响很大。

你需要处理的问题包括：

- 用户提交交易后，页面如何反馈处理中状态
- 前端什么时候重新拉取公开状态
- 结果从“不可公开”切换到“可公开”时，页面如何同步

普通教程常常默认链上状态一改，页面马上就能自然显示结果。  
但在完整 dApp 里，你必须显式设计这个同步过程。

### 第四层：权限与展示层

这是 Zama 教程里最值得反复强调的一层。

因为它不是简单的“管理员能做什么，用户能做什么”，而是：

- 什么结果应该对所有人公开
- 什么结果只对特定角色可见
- 什么阶段应该只展示流程状态，而不展示数值细节

在私密投票中，前端最理想的表达往往不是“什么都给”，而是“按阶段给对的信息”。

## 一个完整 dApp 的页面应该怎么拆

为了让教程更有产品感，建议把页面先控制在三屏以内。

### 页面一：投票首页

这里展示公开元信息：

- 投票标题
- 投票说明
- 候选项列表
- 开始时间和结束时间
- 当前是否处于投票期

这个页面的作用不是“炫技”，而是让用户第一眼知道：

- 这是什么投票
- 我现在能不能投
- 我是否已经投过

### 页面二：投票交互区

这里负责：

- 连接钱包
- 选择候选项
- 提交投票
- 展示交易发送中、确认中、完成后的状态

这一屏最关键的不是视觉设计，而是状态反馈。  
用户必须知道自己到底停留在哪一步，否则一旦链上交互慢一点，体验就会立刻变差。

### 页面三：结果展示区

这里要明确区分三种阶段：

- 投票未结束：展示“结果暂不可见”
- 投票已结束但尚未进入公开阶段：展示“正在生成最终结果”或等效提示
- 结果公开后：展示最终票数、获胜者、结束状态

这样用户不会把“暂时看不到结果”误解成页面坏了。

## 前端文案为什么也属于系统设计

这是中文教程很容易忽略、但很值得讲的一点。

在普通 dApp 里，很多前端提示只是附属信息。  
但在 FHE 应用里，提示文案本身会直接影响用户是否理解系统。

例如下面几种提示，效果就完全不同：

- “读取失败”
- “暂无数据”
- “投票仍在进行中，结果将在结束后公开”

第三种显然更好，因为它把“现在看不到结果”解释成系统规则，而不是异常。

所以完整 dApp 教程里，建议明确告诉读者：

- UI 文案不是装饰
- 对隐私应用来说，文案是帮助用户理解可见性边界的重要组成部分

## 合约和前端之间最容易脱节的地方

做私密应用时，下面几类脱节最常见。

### 1. 时间状态脱节

合约已经进入结束阶段，但前端仍然展示“可投票”。

这通常是因为前端没有在正确时间刷新公开状态，或者本地时间与链上时间逻辑混淆了。

### 2. 权限状态脱节

合约规则规定某些结果还不能展示，但前端写成了默认读取并渲染。

这会让页面不是报错，就是把不可读状态误判成空值。

### 3. 交易状态脱节

用户点击提交后，链上交易已经发送，但页面没有明确提示，用户以为没反应，于是再次点击，造成重复操作或混乱。

所以在完整 dApp 阶段，你不仅要讲功能，还要讲“前端怎样诚实地表达链上状态”。

## 一个推荐的前端状态模型

你可以把页面状态简化成下面几类：

- `idle`：尚未交互
- `wallet_not_connected`：钱包未连接
- `ready_to_vote`：可以投票
- `submitting`：交易提交中
- `confirming`：等待链上确认
- `voted`：已经投票
- `voting_closed`：投票已结束
- `result_available`：结果可查看
- `error`：交互失败

这个模型的好处是，读者可以直接看到：  
前端并不是只围绕“拿到数据”在设计，而是围绕“用户当前所处流程阶段”在设计。

## 一个更接近真实产品的目录建议

如果后面你打算把案例继续做成真正可运行的项目，目录可以大致按下面拆：

- `contracts/`：合约源码
- `test/`：合约测试
- `deploy/`：部署脚本
- `frontend/`：前端项目
- `docs/`：教程与图示说明

前端内部再继续拆：

- `components/`：通用组件
- `features/voting/`：投票主流程
- `lib/`：链上交互与工具函数
- `hooks/`：钱包和链状态相关逻辑

即使暂时不实现全部文件，这种拆法也能帮助读者理解“完整 dApp 和单个 demo 文件夹”的区别。

## 这一章最值得强调的工程原则

### 原则一：公开与私密分层要明确

不要让所有状态都进入隐私路径。  
只把真正需要保护的内容放进私密计算链路，其余状态尽量保持公开可读。

### 原则二：先让流程成立，再优化体验

一个能稳定完成“连接钱包 -> 投票 -> 等待 -> 查看结果”的粗糙版本，比一个 UI 漂亮但状态不可靠的版本更有价值。

### 原则三：前端必须解释系统规则

不要把隐私边界和时间边界留给用户自己猜。

### 原则四：先在本地把交互路径跑通

在 localhost 和 mocked mode 下先把流程做顺，比直接跳到测试网联调更高效。

## 本章完成后的检查标准

如果读者读完这一章，应该能回答这些问题：

- 一个完整私密投票 dApp 至少包含哪几层
- 为什么前端不能简单照搬普通 dApp 的读取逻辑
- 为什么“结果暂不可见”是一种应被明确表达的正常状态
- 完整应用阶段最容易出现哪几类前后端脱节

## 下一章预告

下一章我们会回到最现实的一面：调试与常见坑。

因为只要开始真正写代码，你几乎一定会遇到这些问题：

- 环境明明装好了却跑不起来
- 测试看起来通过了，但前端联调不顺
- 状态读不到，到底是权限问题、逻辑问题还是交互问题

把这些坑提前讲清楚，会极大降低中文读者第一次上手的挫败感。
