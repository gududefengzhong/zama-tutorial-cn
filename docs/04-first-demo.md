# 04. 第一个 Demo

## 本章目标

这一章我们开始把前面三章的内容真正落地。

目标不是一步到位做一个完整产品，而是带读者完成一个最小但完整的闭环：

1. 理解一个“私密投票最小版”应该长什么样
2. 知道这个示例为什么适合做第一个 Demo
3. 明确合约、测试、部署和前端各自需要承担什么职责
4. 为下一步真正写代码打好设计基础

如果前三章解决的是“为什么”和“怎么准备”，这一章解决的就是“第一个例子到底该怎么选、怎么拆、怎么讲”。

## 为什么第一个 Demo 不建议从计数器开始

很多教程都喜欢从计数器开始，因为它足够简单。

但对 Zama / FHEVM 教程来说，计数器有一个问题：  
它很容易让读者只看到“这是一个加密版数值变量”，却看不到真正重要的东西。

而我们真正希望读者尽早理解的是：

- 数据为什么不能公开
- 输入为什么不是普通交易参数
- 合约为什么可以处理密文状态
- 结果为什么不是所有人都能立刻看到

从这个角度看，“私密投票最小版”比“私密计数器”更适合作为第一个案例。因为它天然包含了规则、输入、权限和结果可见性四个维度。

## 我们要做的示例长什么样

这个 Demo 的目标很克制，只做一件事：

让用户对若干候选项提交一票，并在投票结束后查看最终结果。

第一版只保留最核心的功能：

- 合约部署者创建一次投票
- 用户对一个候选项投票
- 每个地址只能投一次
- 投票结束前，不公开完整结果
- 投票结束后，展示最终统计结果

先不要引入这些复杂能力：

- 多轮投票
- 权重投票
- 身份白名单
- 排名投票
- 前端花哨交互

这样做不是保守，而是为了让“第一个闭环”足够短。对新手来说，能跑通一个结构清楚的最小示例，比看一个复杂但难以理解的大 demo 更有帮助。

## 这个 Demo 想让读者学会什么

如果设计得当，这个例子能让读者第一次真正理解四个问题。

### 1. 什么是公开状态

例如：

- 投票标题
- 候选项列表
- 开始时间
- 结束时间
- 某个地址是否已经投票

这些数据通常不需要保密，公开反而更方便系统运行和前端展示。

### 2. 什么是私密状态

例如：

- 某个用户具体投给了谁
- 每个候选项在投票进行中的内部计数

这些信息如果提前公开，就会削弱私密投票的意义。

### 3. 什么是最小权限设计

这个案例会让读者第一次意识到：

- 不是所有信息都该对所有人开放
- “能参与计算”不等于“能直接看到原文”
- “结果何时公开”本身就是业务规则的一部分

### 4. 为什么测试要先于前端

Zama / FHEVM 这类应用的调试成本，比普通合约更高。

所以最稳的做法不是先做页面，而是先保证：

- 合约规则设计清楚
- mocked mode 下的测试可以跑通
- 本地部署路径明确

等这些都成立之后，再补前端，整个过程会顺很多。

## Demo 的最小数据模型

为了让教程容易讲清楚，我们先定义一个极简版本的数据模型。

### 公开数据

- `title`：投票标题
- `options`：候选项名称列表
- `startTime`：开始时间
- `endTime`：结束时间
- `hasVoted[address]`：某地址是否已经投过票
- `isFinalized`：结果是否已经进入可公开阶段

### 私密数据

- 用户投给了哪个候选项
- 每个候选项在投票过程中的票数累计

这里最关键的不是字段名，而是分层思路：  
你要让读者看懂“哪些东西公开对系统没有伤害，哪些东西提前公开会破坏产品目标”。

## 最小交互流程

可以把这个 Demo 的第一版流程理解成下面五步：

1. 部署合约并初始化投票主题
2. 前端或脚本读取公开的投票元信息
3. 用户提交一次私密投票输入
4. 合约记录该地址已投票，并更新私密计票状态
5. 投票结束后，系统公开最终结果

这五步里，最需要教程重点解释的是第 3 步和第 4 步。

因为普通 dApp 教程大多只会讲：

- 用户发交易
- 合约改状态

但在 FHE 场景里，我们更需要讲：

- 输入在进入合约前是什么形态
- 合约里哪些状态是公开的，哪些是密文的
- 结果为什么不能像普通 `view` 一样立即暴露

## 推荐的开发顺序

为了让读者更稳地上手，建议按下面顺序构建这个示例。

### 第一步：先写合约接口和公开状态

不要一上来就写全部隐私逻辑。先把最基础的公开结构定义清楚，例如：

- 创建投票
- 读取公开元信息
- 记录地址是否已投票
- 控制投票是否结束

这样读者能先建立对业务边界的理解。

### 第二步：再接入私密投票输入和私密计票逻辑

这时再讲 FHE 输入、密文状态和相关操作，会更容易被接受。因为读者已经知道整个系统想达成什么目标。

### 第三步：在 mocked mode 下先写测试

根据官方文档，mocked mode 非常适合本地快速测试，因为它能提供更快的反馈，也更适合调试和代码覆盖率分析。对教程来说，这一步非常关键。

建议第一批测试只覆盖主流程：

1. 可以成功创建投票
2. 用户可以成功投一次票
3. 用户不能重复投票
4. 投票结束前后行为符合预期

### 第四步：最后再补部署和前端

只要前面三步稳住，部署脚本和前端交互就会容易很多。否则读者很容易把问题混在一起，不知道自己卡在合约、环境、前端还是网络。

## 这章要如何向读者解释“本地模式”

这是很值得单独讲的一点。

根据官方当前说明，FHEVM 的 Hardhat 开发大致可以分成三种运行场景：

- Hardhat 默认内存网络：使用 mock encryption，适合快速测试和 CI
- Hardhat 本地节点：也是 mock encryption，但适合做持续状态、本地部署和前端联调
- Sepolia：使用真实加密，适合更接近真实环境的验证

对第一个 Demo 来说，我们建议读者主要停留在前两层：

- 测试先跑 in-memory mocked mode
- 需要前端联调时再跑 localhost 节点

不要过早跳到 Sepolia。  
这是教程设计里一个非常重要的“减压动作”。

## 本章可以怎样组织写作

如果你后面要继续把这章补成完整教程，我建议用下面这个结构：

1. 先展示最终要做成什么
2. 再解释为什么选私密投票
3. 再给出最小功能清单
4. 再画出公开状态和私密状态的分层
5. 最后给出开发顺序和测试重点

这样读者不会一打开章节就看到一大段代码，而是先知道自己到底在做什么。

## 一个适合放在章节里的示意图

后面你可以在这章补一张简单流程图，大致像这样：

```text
用户输入候选项
    ↓
前端处理为私密输入
    ↓
合约接收投票
    ↓

    ↓
更新私密计票状态
    ↓

```

即使还没上图形化图表，仅用这种文本流程图，也足够帮助新手建立第一层理解。

## 本章完成后的检查标准

如果读者读完这一章，应该能回答这些问题：

- 为什么第一个 Demo 选私密投票，而不是普通计数器
- 这个示例里哪些状态公开，哪些状态私密
- 为什么测试应先于前端
- mocked mode 和 localhost 节点分别适合什么
